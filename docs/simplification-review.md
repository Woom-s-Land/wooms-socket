# Netty 코드 간소화 진단

기준: 2026-11-06 작업 폴더의 `wooms-socket`, 미커밋 RoomQueue 변경 포함. Builder가 Ponytail audit 지침을 활용해 정적 분석했다. 게임 일부와 Backend·Frontend 계약 전체는 살펴보지 않았고 테스트나 재현 실험은 실행하지 않았다. 아래는 확정된 삭제 목록이 아니라 검증이 필요한 후보들이다.

## 우선 살펴볼 가능성 있는 버그

### 실패한 마피아 참가 기록이 남을 수 있음

- 위치: `NativeHub`의 `mafiaRooms`와 `MafiaGameRepository`의 세션·방 매핑.
- 현재: Hub가 참가 처리 전에 방을 기록하는 반면, Repository는 참가 성공 후 기록한다.
- 우려: 닉네임 중복이나 정원 초과로 참가가 거부되어도 Hub 기록이 남아, 같은 연결의 다른 방 참가를 막을 수 있다.
- 후보: 참가 결과와 세션 소유권을 하나의 권위 있는 기록으로 관리한다. 참가 실패·동시 요청·연결 종료 경로를 함께 확인한다.
- 검증: 참가 거부 후 다른 방 참가 성공을 재현하고, 기존 참가·퇴장·소유권 테스트를 통과해야 한다. 아직 정적 분석에 따른 가능성이며 실제 재현 전이다.

## 작은 범위에서 정리할 후보

| 위치 | 현재 역할과 간소화 방향 | 확인할 영향 |
| --- | --- | --- |
| `SketchService.Wall.cookie`, `BackendBridge.putWall` | 주기 저장을 위해 쿠키를 보관하지만 현재 `putWall`은 내부 저장 키를 사용한다. 미사용 필드·인자 제거 검토. | 모든 호출 경로와 내부 저장 인증 유지 여부 확인. |
| `NativeHub`의 65,536바이트 검사, WebSocket 파이프라인 크기 제한 | 두 곳의 제한이 기본값에서는 겹치지만 하나는 하드코딩이다. 중복을 없애거나 설정을 공유한다. | 프레임과 결합된 메시지의 제한 범위, null·직접 호출·오류 응답을 확인한다. 설정을 늘렸을 때도 일관돼야 한다. |
| `BackendBridge` 내부 요청과 일반 요청 | URI·타임아웃·요청 전송·응답 처리 코드가 반복된다. 공통 부분 통합 검토. | 내부 저장용 비밀키와 사용자 쿠키의 헤더가 섞이지 않아야 한다. 저장과 인증 테스트 필요. |
| `NativeHub` 인증 실패 종료 | 실패 시 여러 경로에서 종료를 호출하는 것으로 보인다. 각 실패 경로와 선후 관계를 확인한 뒤 중복 호출 정리. | 종료 전 메시지 차단, 멱등성 및 비동기 인증 경합을 보존해야 한다. |
| `NativeHub.pending`과 `SocketSession.tail` | 세션별 대기 카운터와 작업 체인이 다른 객체에 있어 초기화·정리 코드가 나뉜다. 카운터를 세션에 두는 방안 검토. | 동시 접근, 연결 종료와 남은 콜백, 한도 초과 시 동작을 확인한다. |
| 세부 분기·검사 | `PresenceService`, `SketchService`, `OutboundBus`, `NativeHub`, `RealtimeServer`에 앞 단계와 겹치거나 같은 결과의 분기 후보가 있다. | 다른 직접 호출 경로, 테스트 계약 및 향후 재사용을 확인하고 도달 불가능함이 입증된 경우만 제거한다. |

## 설계 판단이 필요한 후보

### 방별 실행기와 EventLoop

`RealtimeServer`의 EventLoop는 연결과 네트워크 I/O를, `RoomQueue`의 별도 실행기는 방 작업을 담당한다. 분리는 I/O 스레드가 긴 방 작업에 점유되는 영향을 줄이지만 스레드 간 전달과 공유 상태가 늘어난다.

같은 방의 사용자 연결은 서로 다른 EventLoop에 있을 수 있으므로 별도 실행기를 없애더라도 방 상태의 직렬화는 필요하다. 각 작업의 실행 시간·블로킹 여부·접근 스레드를 확인하고, 다른 방과 연결에 미치는 영향을 측정한 뒤 대안을 정한다. 실행기만 삭제해서 해결할 수 있는 문제가 아니다.

### 마피아 락과 방 큐

`MafiaGame`에는 락이 있고 엔진의 여러 상태 변경은 방 큐를 거친다. 실제 모든 진입점과 타이머·종료·예외 경로가 큐 안에서만 실행된다면 락 중복일 가능성이 있다. 직접 호출이나 비동기 콜백이 하나라도 있다면 제거가 위험하므로 호출 경로와 회귀 검증이 선행돼야 한다. 락이 과하다는 이유만으로 제거하지 않는다.

### 그림판 락과 비동기 로딩

`SketchService`의 `synchronized(wall)`과 `wall.load`도 방 큐와 책임이 겹칠 가능성이 있다. 로드·그리기·보관·주기 저장·종료 저장의 진입점과 Future 완료 스레드를 모두 확인해야 한다. 특히 향후 저장을 큐에서 분리하면 동시성 전제가 바뀔 수 있다. 권한 철회와 순서를 맞추는 세션 락은 별도로 검토한다.

### 타이머 스레드

마피아 스케줄러와 그림 저장 스케줄러가 별도로 존재한다. 타이머가 대부분 방 큐에 작업을 넘기는 데 쓰인다면 스레드 수 조정이나 통합을 검토할 수 있다. 작업 지연, 여러 방의 동시 타이머, 종료 순서와 스케줄러 장애의 영향이 바뀌므로 먼저 측정하고 검증한다.

### 토큰 만료 경로

만료 타이머와 인증 경로에서 연결을 닫는 방식 및 오류 메시지가 다를 수 있다. 한 경로로 통합하면 코드가 줄어들 수 있지만 클라이언트가 받는 close code·메시지가 달라지는 프로토콜 변경이 될 수 있다. 프론트 처리와 원하는 정책을 먼저 결정한다.

### 방 상태 수명

`RoomQueue.slots`와 `SketchService.walls`는 방 사용이 끝나도 누적될 가능성이 있다. 미변경 벽의 저장 작업 예약을 피하는 방안과, 빈 방 상태를 실제로 제거하는 방안은 별개다. 제거 시 활성 연결·대기 작업·미저장 데이터·새 요청과의 경합을 고려해야 한다. 방 생성·퇴장 반복과 저장 중 퇴장 시나리오로 검증한다.

## 당장 없애지 않을 근거

- 세션의 `closed`, `terminationStarted`, `closeStarted`는 쓰기 차단과 정리 단계가 달라 단순히 하나로 합치면 권한 철회 종료가 빠질 수 있다.
- Redis 이벤트와 주기 재검증은 각각 즉시 전파와 Pub/Sub 유실 보완 역할을 한다.
- `synchronized(session)`은 권한 철회와 메시지·그림 처리 순서를 지키는 경로가 있으므로 전제 확인 없이 제거하지 않는다.
- `RoomAccessRevocationHandler`는 수신부와 처리부의 경계 및 테스트 대역 역할이 있다. 추상화가 필요한지는 별도 판단한다.

## 권장 순서

1. 마피아 참가 실패 사례를 회귀 테스트로 재현하고 필요하면 수정한다.
2. 사용자 쿠키 보관, 프레임 제한 불일치, HTTP 요청 중복 등 작은 후보를 호출 경로와 테스트로 확인하며 정리한다.
3. 세션 카운터와 중복 분기를 정리한다.
4. 실행기·락·방 상태 수명은 소유권과 성능·장애 시나리오를 먼저 설계한 뒤 작업한다.

이 문서의 후보는 구현 또는 성능 개선 성과가 아니다. 각 변경은 별도 리뷰와 해당 위험에 맞는 검증 후 완료로 기록한다.
