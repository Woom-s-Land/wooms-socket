# WOOMS Netty 서버 정책 안내

기준: 2026-11-08 마피아 제외 작업본. 이 문서는 연결·실시간 전달·권한·장애·종료 정책을 다룬다. 운영 배포 환경의 프록시 설정은 범위 밖이다.

**읽는 법:** “목적”은 코드의 효과에서 설명한 설계 의도다. 숫자의 최초 선택 이유나 측정 근거가 확인되지 않은 경우 임의로 확정하지 않았다. 기본값은 실제 배포 설정에 따라 달라질 수 있다. 문서 작성 시 별도 시험은 실행하지 않았다.

## 전체 흐름

```text
브라우저 → HTTP 핸드셰이크 / Origin 검사 → WebSocket 연결
        → JSON 명령 → 세션별 순서 → 방 권한 확인
        → 방별 작업 큐 → 채팅·이동·그림 → 구독 연결에 전송
                           ↕ Backend HTTP          ↕ Redis 권한 철회
```

기본값은 `SocketProperties`, `application.properties`에 있다. 서버는 기본 `127.0.0.1:8090`, 경로 `/ws`, Backend는 `http://localhost:8080`이다. 바인드 주소가 루프백이므로 다른 호스트에서 직접 접근하려면 배포 설정이 필요하다. HTTP 인증 전에 WebSocket 연결 자체는 가능하며, 방 접근 시 인증한다.

## 연결과 파이프라인

코드: `src/main/java/com/ee06/mychat/realtime/websocket/RealtimeServer.java`.

| 설정 | 현재 동작 | 목적과 판단할 점 |
| --- | --- | --- |
| `NioEventLoopGroup` boss 1, workers 4 | boss는 연결 수락, workers는 연결의 I/O와 파이프라인 처리 | 연결마다 스레드를 만들지 않고 나눠 처리. 1·4의 적정성은 환경과 부하로 판단해야 한다. |
| `NioServerSocketChannel` | Java NIO 기반 서버 소켓 | Netty에서 비차단 I/O를 쓰기 위한 선택. |
| `SO_BACKLOG=128` | 아직 수락되지 않은 연결의 대기열 크기를 OS에 요청 | 순간적인 접속 폭주 흡수 목적. OS 설정이 실제 값에 영향을 주며 동시 접속 최대치가 아니다. |
| `TCP_NODELAY=true` | 작은 TCP 쓰기를 Nagle 알고리즘으로 모으는 것을 비활성화 | 작은 실시간 메시지의 대기 감소를 기대. 패킷 수와 실제 효과는 측정 필요. |
| 송신 watermark 64 KiB / 256 KiB | 대기 쓰기 양에 따라 채널 writable 상태가 바뀜 | 버퍼 증가 감지. 엄격한 메모리 상한이나 생산자 속도 제어는 아니다. |
| `children` 채널 그룹 | 연결된 채널을 추적해 종료 시 닫음 | 서버 수명과 연결 정리. |

파이프라인은 연결마다 만들어진다. 일반적으로 inbound는 앞에서 뒤로 전달된다. 핸들러가 이벤트를 전달하지 않으면 거기서 멈춘다.

| 순서 | 핸들러 | 하는 일과 의미 |
| --- | --- | --- |
| 1 | `HttpServerCodec` | 핸드셰이크용 HTTP 요청을 해석하고 HTTP 응답을 인코딩한다. |
| 2 | `HttpObjectAggregator` | 나뉜 HTTP 요청을 합친다. 크기 제한은 `max-frame-bytes`, 기본 65,536바이트다. |
| 3 | `OriginGate` | Origin이 있으면 허용 목록과 정확히 비교한다. 기본은 localhost 5173·3000. 거부 시 HTTP 오류 후 종료한다. Origin이 없으면 허용하며, Cookie를 채널에 보관한다. Origin은 인증을 대신하지 않는다. |
| 4 | `WebSocketServerProtocolHandler` | `/ws` 핸드셰이크와 WebSocket 프로토콜을 처리한다. 생성자의 `true`와 프레임 제한 등은 Netty 설정으로 전달된다. |
| 5 | `WebSocketFrameAggregator` | 여러 프레임으로 나뉜 WebSocket 메시지를 합친다. 기본 한도 65,536바이트. HTTP aggregator와 대상이 다르다. |
| 6 | `IdleStateHandler(60,0,0)` | 60초간 읽기 이벤트가 없으면 reader-idle 이벤트를 발생시킨다. 뒤의 핸들러가 연결을 닫는다. |
| 7 | `FrameHandler` | 연결 후 세션 생성 및 텍스트 프레임 전달, idle·연결 종료·예외 처리를 맡는다. |

프레임 크기 제한은 WebSocket 파이프라인의 `max-frame-bytes` 설정에서 관리한다. 초과 시 연결 종료 여부는 해당 Handler의 처리에 따른다.

## 메시지·작업 순서와 과부하

코드: `websocket/NativeHub.java`, `room/RoomQueue.java`, `session/OutboundBus.java`.

| 정책 | 현재 동작 | 이유와 한계 |
| --- | --- | --- |
| JSON 명령 | `PING`, `SUBSCRIBE`, `UNSUBSCRIBE`, `SEND`만 허용 | 지원하는 동작을 명확히 제한. 목적지와 구독 ID도 검증한다. |
| 세션별 순서 | `SocketSession.tail`의 Future 체인으로 한 연결의 명령을 순서대로 처리 | 앞선 비동기 작업이 완료되어야 다음 명령 실행. 느린 작업은 같은 세션의 후속 명령을 지연시킬 수 있다. |
| 세션 대기 256개 | 미완료 명령이 256개를 초과하면 해당 채널을 닫음 | 한 연결의 무한 대기 억제. 숫자의 부하 기반 근거는 확인되지 않았다. |
| 구독 32개 | 세션당 최대 32개의 서로 다른 구독 ID | 구독 상태 증가 제한. 정당한 다중 방 사용에 충분한지는 확인 필요. |
| 방별 실행기 | 기본 4개 `DefaultEventExecutorGroup` 실행기를 방 ID 해시로 선택 | I/O와 방 작업을 분리하고 제한된 스레드를 공유. 별도 그룹 자체가 필수는 아니며 블로킹 작업은 같은 실행기의 다른 방도 지연시킨다. |
| 방별 Future 체인 | 이전 작업의 `CompletionStage`가 완료된 뒤 다음 작업을 실행 | 방 상태의 순서 보장. HTTP 대기는 스레드를 점유하지 않아도 해당 방의 후속 작업을 지연시킨다. |
| 방 대기 2,048개 | 초과 시 실패 Future 반환 | 대기 작업 폭증 억제. 숫자의 측정 근거는 확인되지 않았다. |
| 느린 수신자 | 쓰기 시 `isWritable()`이 거짓이면 연결을 닫음. 전송 실패도 연결 종료 | 느린 연결의 버퍼 증가를 억제. 이는 백프레셔가 아니라 연결 종료 정책이며, 재연결과 메시지 유실의 사용자 영향을 확인해야 한다. |
| 종료 중 큐 접수 | `closed`면 `RejectedExecutionException` | 종료 후 접수 거절 의도. 검사와 종료의 경합, 호출 측 실패 처리, 중복 동기화는 별도 검토 대상이다. |

방 큐 슬롯과 그림 상태를 미사용 방 기준으로 제거하는 경로는 현재 확인되지 않았다. 장기간 방 수가 증가하면 상태 누적 가능성을 검토해야 한다.

## 인증과 권한 철회

코드: `websocket/NativeHub.java`, `backend/BackendBridge.java`, `access/redis/`, Backend의 `domain/realtime/access`와 `WoomsService.leaveWooms`.

- 핸드셰이크에서 확보한 쿠키로 최초 방 접근을 Backend에 확인한다. 사용자 신원과 가입 권한은 Backend가 소유한다. 연결 자체는 인증 전 허용되므로 미인증 연결의 자원 소모 정책은 별도로 필요하다.
- 인증 결과 캐시 TTL은 기본 60초, 연결별 재검증은 30~60초의 무작위 간격이다. 메시지를 보내지 않고 구독만 유지하는 연결도 재검증한다. 분산은 요청 집중을 줄이기 위한 선택이며 간격의 적정성은 측정·보안 정책에 따라 결정한다.
- 토큰 만료 시각에 종료 작업을 예약한다. 스케줄링 지연까지 포함한 절대적인 시한 보장은 별도 확인이 필요하다.
- Backend 401/403 및 일부 4xx는 권한 거부, 408/429와 서버 오류·타임아웃 등은 일시 장애로 분류한다. 각각 WebSocket close 4403, 1013을 사용한다. 일시 장애에서도 접근을 계속 허용하지 않고 연결을 종료한다.
- Backend 요청 연결 및 요청 타임아웃은 기본 5초. 비동기 `HttpClient.sendAsync`를 사용한다. 이 값의 최적성, 전체 동시 요청 상한과 장애 시 재시도 정책은 별도 점검이 필요하다.
- Backend 탈퇴 트랜잭션 커밋 후 Redis 채널 `wooms.realtime.access.v1`로 철회 이벤트를 전달한다. Netty는 방과 사용자 일치 여부를 확인하고 대상 연결을 닫는다. 한 연결이 여러 방을 쓰면 그 연결의 다른 방도 함께 끊긴다. 관리자 강퇴 기능은 현재 별도 구현되어 있지 않다.
- 최초 인증 응답이 오기 전에 철회가 오면 해당 방의 진행 중 인증에 대상 UUID를 기록해, 늦은 응답이 철회된 사용자에게 권한을 부여하지 못하게 한다. 다른 사용자와 다른 방의 인증은 보존한다.
- Redis 리스너 복구 간격은 30초. Pub/Sub은 끊긴 동안 메시지를 보관하지 않고, 이 구현에 outbox는 없다. 주기 재검증이 유실을 보완하지만 정확히 60초 이내 철회를 보장한다고 단정할 수 없다. 중복 이벤트 ID는 최근 4,096개를 메모리에 기억한다. 재시작 후에는 기억이 사라진다.

## 연결 수명과 그림 저장

코드: `../wooms-frontend/src/libs/socket/NettyClient.js`, socket의 `sketch/SketchService.java`.

- 프론트는 기본 10초마다 JSON `PING`을 보내고 `PONG`을 받는다. 3개 간격 동안 수신 활동이 없으면 연결을 닫는다. 서버는 60초간 수신이 없을 때 닫는다. 시간 감지는 타이머와 스케줄링에 좌우된다.
- 프론트 재연결 간격 기본값은 고정 5초다. 대규모 동시 장애 후 동시 재연결 가능성이 있어 분산 여부를 검토할 수 있다.
- 그림은 방별 메모리에 유지하고 5초마다 변경된 상태를 Backend에 비동기 저장한다. 방 큐가 저장 응답을 기다리는 동안 그 방의 다른 작업도 대기한다. 저장 실패 시 로그를 남기고 다음 기회에 재시도할 수 있다.
- 보관 요청은 Backend 성공 후 캔버스를 초기화한다. 저장 실패 시 초기화하지 않는 정합성 선택이지만 응답 지연이 방에 전파된다.
- 정상 종료 시 변경된 그림의 마지막 저장을 시도하고 최대 5초 기다린다. 강제 종료나 타임아웃 시 저장을 보장하지 않는다. 종료 순서 및 진행 중 작업의 실제 완료 보장도 장애 실험이 필요하다.

## 검증 현황과 우선 확인할 질문

- 기존 기록: socket `clean test bootJar` 테스트 27개 실패 0, 최종 독립 리뷰 승인. 실제 Redis·H2 Backend·Netty 로컬 통합은 통과했으나 최종 방 범위 수정 전 실행이다. 운영 검증이나 이번 문서 작성 중 재실행을 의미하지 않는다.
- 그림 저장을 지연시키면 같은 방 채팅 p95/p99가 얼마나 늘어나는가? 저장 분리 시 스냅샷·버전·보관 순서를 어떻게 보장할 것인가?
- 방별 실행기와 세션 락·`volatile` 각각의 소유권과 접근 스레드는 무엇인가? 안전하게 단순화할 수 있는가?
- 4개 방 스레드, 256·2,048 대기 한도, 64/256 KiB watermark, 5초 timeout의 선택 근거와 실패율은 무엇인가?
- Redis 단절·Backend 장애·동시 재연결·정상/강제 종료에서 실제 사용자에게 어떤 오류와 데이터 유실이 발생하는가?
- 빈 방 상태 정리와 미인증 연결 수명·개수 제한이 필요한가?
